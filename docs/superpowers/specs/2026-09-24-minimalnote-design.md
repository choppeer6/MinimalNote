## 1. 问题

日常碎片化记事的摩擦,不在于"记不下来",而在于**记事这个动作本身太重**:

> 解锁 → 找到 App → 等启动 → 找"新建" → 输入 → 保存

这套走完,想记的那件事已经凉了。结果是该记的没记、该做的没做,待办清单逐渐沦为摆设。

## 2. 目标

1. **把"记一笔"压到一步** —— 桌面卡片上直接勾选或输入,不开 App
2. **让"要不要做"成为唯一决策** —— 记录时不必先想"这是待办还是笔记"
3. **让进度可见** —— 周/月完成度可视化,支撑习惯养成

### 非目标

- 不做云同步 / 多端协作(数据全部留在本机)
- 不做团队协作 / 共享清单
- 不做富文本编辑器 —— 要的是"小记",不是文档工具

---

## 3. 已确认决策

| 编号 | 决策项 | 结论 | 理由 |
|---|---|---|---|
| **D1** | 主导航 | **三 Tab:待办 / 统计 / 我的** | 统计是核心卖点,需要有稳定的家;设置类功能不挤主界面 |
| **D2** | 数据模型 | **统一条目(Item)模型** | 碎片化记事的真实动作是"先记下来,回头再决定要不要做"。记录时逼用户分类,反而制造摩擦 —— 与"操作繁"的痛点自相矛盾 |
| **D3** | 平台 | HarmonyOS ArkTS / ArkUI | 依赖服务卡片、代理提醒等鸿蒙特有能力 |
| **D4** | 存储 | 本地,不上云 | 隐私 + 免登录 + 启动快 |
| **D5** | 视觉语言 | **纸墨(paper & ink)** | 暖米白纸面 / 墨黑文字 / 低饱和"颜料"标签色 / 楷体点缀。契合"小记"的手记气质,刻意避开通用 AI 审美 |

## 4. 数据模型

单一实体 `Item`,用 `kind` 区分两种状态 —— **这是 D2 的落地形式**。

```ts
type Tag  = '学习' | '工作' | '生活';
type Prio = 'high' | 'mid' | 'low';

interface Item {
  id:        number;          // 自增主键
  kind:      'todo' | 'note';
  title:     string;          // 正文(语音转写结果最终也落到这里)
  tag:       Tag;
  prio:      Prio | null;     // 仅 todo 有值
  due:       string | null;   // ISO 8601,仅 todo 有值;null = 不提醒
  done:      boolean;         // 仅 todo 有意义
  doneAt:    string | null;   // ISO 8601,用于统计归属日
  createdAt: string;          // ISO 8601
  imageUris: string[];        // 图片附件,可为空
}
```

**关键约定**

- `kind === 'note'` 的条目:`prio` / `due` / `doneAt` 恒为 `null`,**不参与完成度统计**
- `kind` 可升格:`note → todo`(加个截止时间就变成待办),反向降格不提供
- 日期一律 ISO 8601 存储,展示层格式化为 `M月D日 星期X` / `H:mm`
- 示例合成值:`{"id":101,"kind":"todo","title":"背 50 个单词","tag":"学习","prio":"mid","due":"2026-09-24T21:00:00+08:00","done":false,"doneAt":null,"createdAt":"2026-09-24T09:41:00+08:00","imageUris":[]}`

## 5. 信息架构

```
App
├── 待办 Tab(默认)
│   ├── 日期 + 今日进度条
│   ├── 抓取框「记点什么…」→ 新建面板
│   ├── 分组:待办(kind=todo)
│   └── 分组:随手记(kind=note)
├── 统计 Tab
│   ├── 本周完成度环形图 + 三项汇总
│   ├── 每日完成柱状图
│   ├── 标签分布
│   └── 连续打卡
└── 我的 Tab
    ├── 彩色标签管理
    ├── 代理提醒开关
    ├── 桌面卡片尺寸
    ├── 语音识别设置
    └── 数据存储说明

桌面服务卡片(绕开 App 的第二入口)
├── 今日待办 3–4 条,可直接勾选
└── 「记一笔」快捷入口
```

**设计要点**:待办与随手记在 UI 上分两组呈现,但底层是**同一个数组、同一张表** —— 只是按 `kind` 分流渲染。用户不需要理解这个概念,他只看到"要做的"和"记下的"各自归位。

## 6. 功能分解与鸿蒙技术映射

| # | 功能 | 鸿蒙能力 | 权限 / 备注 |
|---|---|---|---|
| 1 | 桌面服务卡片快捷打卡 | `FormExtensionAbility` + ArkTS 卡片;卡片点击经 `postCardAction` 回传,`formProvider.updateForm()` 刷新 | App 与卡片可能不同进程,状态需经 RDB 共享 —— **见未决问题 U2** |
| 2a | 文本快速记事 | 纯本地 | — |
| 2b | 语音转文字 | Core Speech Kit 语音识别 | `ohos.permission.MICROPHONE` |
| 2c | 图片附件 | `photoAccessHelper` / 文件选择器 | 建议用 Picker,免申请读媒体权限 |
| 2d | 彩色标签 | 本地枚举 + 色板 | — |
| 3 | 优先级与定时提醒 | `reminderAgentManager` 代理提醒 | `ohos.permission.PUBLISH_AGENT_REMINDER` |
| 4 | 可视化统计 | Canvas 自绘,或三方图表库 | 数据量小(周/月聚合),自绘 Canvas 足够且无依赖 |

**渲染层**:列表用 `List` + `LazyForEach`;卡片为独立 ArkTS 模块(entry 下的 form 目录)。

## 7. 统计口径

**只统计 `kind === 'todo'` 且 `done === true` 的条目**,按 `doneAt` 归属到自然日。

- **本周完成度** = 本周实际完成数 ÷ 本周计划数
  - 计划数口径——**待定,见 U4**
- **每日完成柱状图**:周一 → 周日,未来日期不显示数据
- **标签分布**:按完成件数占三标签比例
- **连续打卡**:当天至少完成 1 件待办即算打卡

随手记(`note`)在任何统计中都不出现。

## 8. 视觉语言 · 纸墨

| 角色 | 值 | 用途 |
|---|---|---|
| 纸面 | `#F6F2EA` | 主背景,暖米白而非纯白 |
| 卡片 | `#FFFDF9` | 浮起面 |
| 墨 | `#1C1A17` | 主文字 |
| 次级墨 | `#554E44` / `#968D7F` | 元信息、弱文字 |
| 朱砂 | `#C2410C` | 强调色:进度、今日、主按钮 |
| 靛青 `#3F5E8C` | 学习 | 标签 |
| 赭石 `#B4553A` | 工作 | 标签 |
| 苔绿 `#5A7A52` | 生活 | 标签 |

- **字体**:标题与记事正文用霞鹜文楷(手写楷体),界面文字用系统无衬线。楷体只用在"内容"上,不用在控件上 —— 保住手记气质,不牺牲可读性
- **夜记主题**:深底 `#141311`,同色系提亮,朱砂转为 `#E0703A`
- **质感**:全局叠加极低透明度噪点模拟纸面;卡片用 26px 模糊 + 半透明,呼应鸿蒙原生卡片质感
- **动效**:勾选时方框填充 + 对勾描边 + 标题划线依次发生;柱状图错峰生长;底部导航指示块弹性滑动

## 9. 未决问题

| 编号 | 问题 | 影响 |
|---|---|---|
| **U1** | 目标 API 版本?是否 HarmonyOS NEXT(API 12+)? | 决定能否用 `@kit.*` 形式导入,以及 `reminderAgentManager` 的可用性 |
| **U2** | 卡片与 App 的数据同步机制:RDB 轮询 / `formProvider` 主动刷新 / 共享 Preferences? | 这是**功能 1 的技术核心**,方案不定则卡片做不出来 |
| **U3** | 待办是否需要"重复"规则(每日/每周)? | "背 50 个单词"天然是循环任务,当前模型不支持,只能手动重建 |
| **U4** | "本周计划数"的口径 —— 按 `due` 落点还是按创建时间? | 直接决定完成度百分比的分母,影响统计可信度 |
| **U5** | 统计页的"日均专注时长"从哪来? | 原型里是我编的(1.8 小时)。当前数据模型**完全没有**可推导专注时长的字段 |
| **U6** | 语音识别是离线还是在线?支持方言吗? | 影响权限声明与包体积 |
| **U7** | App 被杀死后,代理提醒是否仍需触发? | 决定用 `reminderAgentManager` 还是普通通知 |

> **U5 需要特别注意**:这是原型里唯一一处凭空捏造的数据指标。要么砍掉,要么补采集机制(例如记录 `startedAt` / `doneAt` 差值)。在补上之前,统计页不应展示这个数字。
